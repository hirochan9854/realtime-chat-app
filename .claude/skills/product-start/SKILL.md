# Product Start Workflow

See @references/templates.md for document and task file templates.

このワークフローは SDD（仕様駆動開発）に基づく。

ultrathink

## Phase 1: 初期化

docs/spec/, docs/adr/, tasks/, tasks/lessons.md を作成。

既存ドキュメントの確認:
- docs/spec/ に既存ファイルがある場合: 内容を読み取り「これをベースに進めますか？」と確認
- ユーザーから仕様書を受け取った場合: その仕様書を元に読み解き、不明点を Phase 2 で質問する
- **仕様書が既に存在する場合でも、受け取った仕様書を元に改めて docs/spec/ に構造化した仕様書を作成する**

## Phase 2: ヒアリング（共通）

**原則: 疑問点がゼロになるまで質問を続ける。**
1つずつ質問。AskUserQuestion で選択肢ベース。
曖昧な回答には具体例で確認。矛盾はその場で解決。
全回答を記憶し、全カテゴリ完了後にドキュメント生成。

### カテゴリ: ビジョン
- どんなプロダクトを作りたいか / 解決する課題 / 成功指標

### カテゴリ: ターゲットユーザー
- 誰が使うか / 技術リテラシー / 利用シーン

### カテゴリ: 主要機能
- 最重要機能 / 他の機能と優先度(MoSCoW) / スコープ外

### カテゴリ: ページ構成
- 必要なページ一覧 / 各ページのユーザーアクション / 重要な画面遷移

### カテゴリ: 技術要件
- 認証方式 / 外部サービス連携 / DB要件

### カテゴリ: 非機能要件
- SEO / 多言語 / レスポンシブ範囲 / アクセシビリティ / パフォーマンス

### カテゴリ: スケジュール
- リリース目標 / MVP範囲 / チーム役割分担

## Phase 3: 層インストール（ヒアリング結果に基づく）

ヒアリングの回答を元に、必要な層をインストールする。
**インストールにより新しいスキル・ルール・エージェントが追加され、以降のフェーズが強化される。**

### Step 3-1: プロジェクト種別の判定

**Q: 「何を作りますか？」**

| 回答 | インストールする層 |
|------|------------------|
| Webサービス（SaaS, 管理画面, Webアプリ等） | `/init stack-service` |
| LP / Webサイト | `/init stack-site`（将来） |

→ 選択された層をインストール: `/init stack-service` を実行

### Step 3-2: デザインの有無

**Q: 「既にデザイン（Figma, カンプ, ワイヤーフレーム）はありますか？」**

| 回答 | アクション |
|------|----------|
| **No** — デザインなし | `/init design` を実行 → Phase 4（デザインヒアリング）へ |
| **Yes** — Figma/カンプあり | design 層はインストールしない → Phase 5 へ |

→ デザインがない場合: `/init design` を実行

### Step 3-3: インストール結果の確認

インストール完了後:
- `layers.lock` を確認し、インストール済み層を表示
- CLAUDE.md が更新されていることを確認
- 「以下の開発環境がセットアップされました」と表示

### Step 3-4: ライブラリバージョン確認（MANDATORY）

**⚠️ テンプレートのバージョンをそのまま使ってはいけない。必ず最新を確認する。**

1. インストールされた package.json の依存ライブラリを列挙する
2. Context7 `resolve-library-id` で各ライブラリの最新メジャーバージョンを確認する
   - `Versions` フィールドに最新バージョンが表示される
3. テンプレートより新しいメジャーバージョンがあれば package.json を更新する
4. バージョンアップに伴う設定ファイルの変更が必要か `query-docs` で確認し、必要なら作成・更新する
   - 例: Prisma v7 → `prisma.config.ts` が必要
   - 例: Next.js 16 → `cacheComponents: true` が `next.config.ts` に必要
5. 更新完了後 `pnpm install` を実行する

## Phase 4: デザインヒアリング（design 層がある場合のみ）

**⚠️ この Phase は `/init design` を実行した場合のみ実施する。**
**design 層がインストールされたことで、以下のスキルが利用可能になっている:**
- anti-ai-design（Anti-AIデザイン原則）
- design-system（DS構築フロー）
- figma-sync（Figma連携）
- page-create（ページ作成フロー）
- component-add（コンポーネント追加フロー）

### パス判定

**Q: 「使用したいデザインシステムはありますか？」**

**→ パスB: DSあり & サービスデザインなし:**
1. 使用するDSの名前・バージョン
2. サービスデザインの方向性（UIの雰囲気、参考サイト）
3. DSにない独自コンポーネントの要否
4. ページごとの情報設計の方針

**→ パスA: デザインなし & DSなし（最も質問が多い）:**
以下を1つずつ質問してDS構築 + デザイン方針を固める:
1. 「デザインの方向性はありますか？（色、雰囲気、参考サイト）」
2. 「プライマリカラーの希望は？」
3. 「ブランドカラーとアクセントカラーの関係は？（支配色 + 鋭いアクセント推奨）」
4. 「ダークモード対応は必要ですか？」
5. 「フォントの指定はありますか？」
   - **注意: Inter, Roboto, Open Sans, Lato, Arial 等のデフォルト系フォントは避ける**
   - 推奨例: JetBrains Mono, Fira Code, Space Grotesk, IBM Plex, Bricolage Grotesque
6. 「角丸は多め（柔らかい）か少なめ（シャープ）か？」
7. 「全体的にコンパクト？それともゆったり？」
8. 「モーションの方針は？（ページロード時の段階的表示等）」
9. 「背景の方針は？（単色 / グラデーション / パターン）」

### デザインありの場合（Phase 3 で Yes の場合、design 層なし）

**→ パスC: デザインがある場合（design 層なしでも対応可能）:**
1. 「FigmaファイルのURL（シンボル / サービスデザイン）を教えてください」と求める
2. 「デザインの完成度は？（確定 / ドラフト / 方向性のみ）」
3. 「デザインに含まれない画面・状態はありますか？」
4. Figma MCP (get_screenshot, get_design_context) でデザインの内容を読み取る
5. 読み取ったデザインから色・タイポグラフィ・レイアウトパターンを把握
6. デザインの不明点（状態遷移、ホバー、エラー表示等）を追加で質問

## Phase 5: FW固有ヒアリング（stack 層がある場合）

**⚠️ stack 層がインストールされたことで、FW固有のスキル・ルールが利用可能。**
**これらのスキルの知識を活かして、より具体的な質問ができる。**

stack 層に含まれるスキルの知識に基づいて追加質問:
- アーキテクチャに関する質問（stack 層の architecture ルールに基づく）
- データモデルに関する質問（stack 層の ORM スキルに基づく）
- 認証・APIに関する質問（stack 層の FW スキルに基づく）

---

## Phase 6: ドキュメント生成（順番厳守、各ユーザー確認）

### 全パス共通
1. docs/spec/interview-record.md
2. docs/spec/context-notes.md
3. docs/spec/user-stories.md (MoSCoW + Acceptance Criteria)
4. docs/spec/requirements.md (FR-XXX + NFR-XXX)
5. docs/architecture.md（**stack 層がある場合、そのアーキテクチャパターンを反映**）

### パスA のみ追加（design 層 + DSなし）
6. docs/design-system.md（カラーパレット、タイポグラフィ、スペーシング、コンポーネント方針）

重要判断は docs/adr/ADR-XXX.md に記録。

---

## Phase 7: タスク分解（UI先行開発）

**タスク順序の原則:**
```
1. プロジェクトセットアップ（scaffold 配置、依存インストール）
2. DS構築（パスA: ゼロから / パスC: デザインから抽出）※パスBはスキップ
3. ページUI構築（mock data使用、1ページ単位）
4. DBスキーマ設計（早期に実施、UIと並行可）
5. バックエンド実装（認証、API、Repository実装）
6. 動的化（mock → 実データ切替）
7. テスト
8. デプロイ
```

tasks/TASK-001.md〜。チェックボックス付き Acceptance Criteria と Sub Tasks。

**⚠️ タスクの具体的な内容は stack 層のスキル・ルールに基づいて生成する。**
**stack 層がない場合は汎用的なタスクのみ生成する。**

---

親Issue + Sub-Issue。ラベル + マイルストーン。TASK-XXX.md に URL記録。
